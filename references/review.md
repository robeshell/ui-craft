# 检查与交付

根据任务选择检查范围，不把规范文档任务变成未经请求的构建、装机或发布。下列是设计工作检查方法，不是要求所有任务必须跑完的固定流程。

## 规范交付

- 设计值是否对应明确角色，而不是散落的数值？是否写明逻辑单位及默认字号条件？
- 哪些约束来自用户／现有产品，哪些来自标准，哪些是设计提案？有没有把历史教程建议误写成平台强制要求？
- 是否规定长内容、状态变化和字体放大的处理？是否仅因颜色好看就忽略对比度？
- 来源、保留范围、例外和后续验证方式是否可追溯？

规范可以是 Markdown 表格或项目已有格式，不强制引入新工具。只交付规范时，明确尚未验证渲染。

## 视觉和交互检查

| 检查面 | 实查内容 | 典型失败 |
| --- | --- | --- |
| 功能主次 | 主体面积、阅读动线、判断信息和辅助操作的权重 | 所有模块等大，控制区挤掉主要反馈 |
| 分组与表达 | 信息归属、组内外距离、品牌特征、真实内容与图形 | 靠同款描边套所有分区，只换皮仍像原型 |
| 实际尺度 | 指定逻辑宽度和缩放下看单页，再看全局关系 | 拼图缩小后显得精致，单页却是巨大文字 |
| 文字 | 中文字面、行高、基线、长内容、数字更新、字体缩放 | 数值变化挤动按钮、文字被固定高度裁掉 |
| 色彩 | 实际合成背景、选中／禁用／警示、焦点 | 浅灰字不可读、只靠颜色区分状态 |
| 图标 | 实际尺寸、重量、光学居中、点击范围、可访问名称 | 外框同大而视觉重量悬殊、热区覆盖邻项 |
| 布局 | 目标最窄／典型／较宽窗口，安全区与键盘 | 文字随宽度放大、底部操作被键盘遮挡 |
| 内容状态 | 正常、空、加载、失败、长字段、缺失可选字段 | 用假记录填空、只设计成功状态 |
| 操作过程 | 按下、滚动、切换、展开、返回、取消、异步反馈 | 静态稿正常，切换后错位或按钮不可达 |
| 动效 | 中途打断、反向切换、减少动态效果 | 装饰动画延迟操作、动画掩盖真实状态 |

如果只拥有截图，只能对可见状态作判断；不能宣称按钮可点、滚动正常或无障碍语义正确。网页原型验证不能替代原生平台渲染检查。缺少运行环境时交付能完成的结果，并准确列出未验证项。

## 评审表达

以具体元素和影响描述问题，例如「记录行时间使用浅灰，和白底的对比度为 X，扫描时难读；调整辅助文字角色并复查所有引用」。不要只写“缺乏高级感”。

建议按影响排序：影响读取／操作的问题 → 跨页一致性问题 → 细节优化。通过截图位置、代码位置或组件名定位；没有证据的事项标为待查，而不是确定缺陷。

## 交付证据

保留必要的页面／状态、设备或视口、缩放、代码版本与截图位置。分别说明规则已定义、代码已实现、渲染已检查、交互已验证、用户已接受；不要合并成一个“完成”。以代表性页面和状态支撑结论，避免重复堆截图。
