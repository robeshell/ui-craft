# 检查与交付

本文件是 SKILL.md 第 5 步的细节参考。按任务选检查范围，不把一个规范文档任务变成未经请求的构建、装机或发布。下面是检查方法，不是每次都要跑完的固定流程。

## 检查范围与改动相称

| 改动规模 | 至少检查 |
| --- | --- |
| 局部修正（一个组件、一处间距） | 修改处在典型尺度下的渲染，加上它所在行的相邻元素 |
| 单页重排 | 典型尺度下的完整页面，最窄尺度下的主体区，真实长内容，主要操作的按下和禁用态 |
| 多页或规范整理 | 代表性的两到三个页面，跨页共用组件的一致性 |
| 原生应用 | 目标设备逻辑尺寸，系统字体放大一档，Safe Area 和键盘弹出 |

## 视觉和交互检查表

| 检查面 | 实查内容 | 典型失败 |
| --- | --- | --- |
| 功能主次 | 主体面积、阅读动线、判断信息和辅助操作的权重 | 所有模块等大，控制区挤掉主要反馈 |
| 分组与表达 | 信息归属、组内外距离、品牌特征、真实内容与图形 | 靠同款描边套所有分区，换皮后仍像原型 |
| 实际尺度 | 在指定逻辑宽度和缩放下看单页，再看全局关系 | 拼图缩小后显得精致，单页却是巨大文字 |
| 文字 | 中文字面、行高、基线、长内容、数字更新、字体缩放 | 数值变化挤动按钮，文字被固定高度裁掉 |
| 色彩 | 实际合成背景、选中、禁用、警示、焦点 | 浅灰字不可读，只靠颜色区分状态 |
| 图标 | 实际尺寸、重量、光学居中、点击范围、可访问名称 | 外框同大而视觉重量悬殊，热区覆盖邻项 |
| 布局 | 目标最窄、典型、较宽窗口，安全区与键盘 | 文字随宽度放大，底部操作被键盘遮挡 |
| 内容状态 | 正常、空、加载、失败、长字段、缺失可选字段 | 用假记录填空，只设计成功状态 |
| 操作过程 | 按下、滚动、切换、展开、返回、取消、异步反馈 | 静态稿正常，切换后错位或按钮不可达 |
| 动效 | 中途打断、反向切换、减少动态效果 | 装饰动画延迟操作，动画掩盖真实状态 |

## 证据的边界

- 只有截图时，只能对可见状态下判断。不能宣称按钮可点、滚动正常或无障碍语义正确。
- 网页原型不能替代原生平台的渲染检查。
- 代码审查能发现规则是否写对，不能证明渲染结果。
- 缺少运行环境时交付能完成的部分，并准确列出未验证项。写"未验证"不丢人，写"已验证"但没验证才是问题。

## 规范交付的检查

- 设计值是否对应明确角色，而不是散落的数值？是否写明逻辑单位和默认字号条件？
- 哪些约束来自用户或现有产品，哪些来自标准，哪些是设计提案？有没有把过时的经验值误写成平台强制要求？
- 是否规定长内容、状态变化和字体放大的处理？
- 来源、保留范围、例外和后续验证方式是否可追溯？

规范可以是 Markdown 表格或项目已有格式，不强制引入新工具。只交付规范时，明确写"尚未验证渲染"。

## 评审表达

以具体元素和影响描述问题：

> 记录行的时间戳使用 `#9CA3AF`，和白底的对比度为 2.54:1，扫描列表时难以辨读。建议改用辅助文字角色 `#767676`（4.54:1）并复查其他引用该颜色的位置。

而不是：

> 整体缺乏高级感，细节不够精致。

按影响排序：

1. 影响读取或操作的问题
2. 跨页一致性问题
3. 细节优化

每条通过截图位置、代码位置或组件名定位。没有证据的事项标为"待查"，不写成确定缺陷。

评审的结论可以是"没有需要改的"。页面已经满足任务和规范时，就这样写，列出检查过的项目即可。不要为了让评审看起来有产出而把偏好写成问题，比如"圆角可以再大一点"、"这里可以加个阴影"这类没有依据的意见。

## 交付记录模板

下面这张表只用于页面设计 / 重排和规范整理任务，因为这两类交付需要把"改了什么、验证了什么、没验证什么"分开说清楚。局部修正和评审不附这张表：局部修正只写一句根因加修改，评审只写按影响排序的问题列表，末尾一句话说明哪些没有渲染验证即可。

```markdown
## 实查记录

- 页面 / 状态：…
- 设备或视口：…，缩放 …
- 代码版本：…

| 项目 | 状态 |
| --- | --- |
| 规则已定义 | 是 / 否 |
| 代码已实现 | 是 / 部分 / 否 |
| 渲染已检查 | 是，在 … / 否 |
| 交互已验证 | 是，检查了 … / 否 |
| 用户已接受 | 待确认 |

未覆盖：…
```

以代表性页面和状态支撑结论，避免重复堆截图。
